# Report Templates

Phase 5. Use these structures as written. Consistency is what makes two reviews comparable and
what lets a re-review verify claims.

---

## 1. Finding block (used everywhere)

```markdown
### F-03 · Tax rounding differs between checkout and invoicing
**Severity:** Major · **Confidence:** CONFIRMED · **Effort:** M · **Dimension:** Duplication
**Location:** `api/checkout/tax_calc.py:112-149`, `jobs/invoice_backfill.py:88-120`,
canonical at `services/billing/tax.py:40-78`

**Evidence**
```python
# services/billing/tax.py:61   (canonical)
return amount.quantize(CENT, rounding=ROUND_HALF_EVEN)

# jobs/invoice_backfill.py:104
return round(amount, 2)          # Python round() is half-even on floats, but amount is float here
```

**Why it matters**
The backfill job converts `Decimal` to `float` before rounding, so invoices generated by the
job can differ from the checkout total by one cent on amounts ending in a half-cent. Customer-
visible on the invoice PDF and it breaks reconciliation against the payment provider.

**How to confirm / reproduce**
`amount = Decimal("10.005")` through both paths: checkout yields `10.00`, backfill yields
`10.01`.

**Suggested fix**
Delete the local calculation in `invoice_backfill.py` and call
`services.billing.tax.compute()`; keep `Decimal` end to end. Add a test asserting both paths
agree on half-cent inputs.

**Risk if fixed / not fixed**
Fixing changes historical backfill output — check whether already-issued invoices must be left
alone. Not fixing leaves a permanent one-cent reconciliation drift.
```

Rules for the block:

- Stable IDs (`F-01`, `F-02`) so fixes and re-reviews can reference them.
- The excerpt is the **minimum** that proves the claim — never paste whole files.
- "Why it matters" describes a concrete failure, with the input or condition that triggers it.
- The suggested fix is a direction plus its trade-off, not a rewritten module. Detailed
  implementation belongs to the implementation workflow, not the review.
- If you are unsure, say what would resolve it. Never pad a finding to look thorough.

## 3. PR-comment style (when the user wants inline review comments)

Keep each comment self-contained; reviewers read them out of context.

```markdown
**[Major · CONFIRMED]** This `except Exception` also catches `KeyError` from the parser above,
so a malformed payload is recorded as a successful sync. Narrow it to `RequestError`, or
re-raise anything that is not a network failure.
```

And a summary comment at the top of the PR:

```markdown
**Changes required** — 1 blocker, 3 major, 5 minor.
Blocking: authorization is not checked in the new `/exports` route (`api/exports.py:31`).
Full report: `reports/code-quality-exports-2026-08-18.md`
```

## 4. Snippet review (no repo access)

When the user pastes code with no surrounding context, keep the structure but be explicit about
what you cannot know:

```markdown
**Reviewing in isolation.** I can judge internal logic, error handling, and structure; I cannot
verify callers, duplication elsewhere, or whether this is wired up. Findings marked
`SUSPECTED` need repo context.
```

Then findings, then a short list: "To finish this review I would need: the caller of `sync()`,
the definition of `Client.fetch`, and whether `settings.RETRIES` has a default."

## 5. Re-review after fixes

Verification is the point — do not accept "fixed" on assertion.

```markdown
# Re-review — <scope> @ <new sha>

| Finding | Claimed | Verified | Notes |
|---|---|---|---|
| F-01 authz gap | fixed | ✅ confirmed | check added at `api/exports.py:34`, test at `tests/test_exports.py:88` |
| F-03 tax rounding | fixed | ⚠️ partial | checkout path fixed; `jobs/invoice_backfill.py:104` unchanged |
| F-07 missing timeout | fixed | ❌ not fixed | timeout added to one of three clients |

**New issues introduced by the fixes:** <finding blocks, or "none">
**Updated verdict:** <…>
```

Always re-check for issues *introduced* by the fixes. Fix-induced regressions are common,
especially when a fix was made under time pressure to clear a Blocker.
