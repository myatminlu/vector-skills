# 12 — Go Layouts

## TL;DR

- Small tool → **flat**: `main.go` + a few files in one package. Structure at pain, not at birth — Go's stdlib culture is anti-ceremony.
- Grown service → `cmd/<binary>/main.go` (thin) + `internal/<feature>/` packages. `internal/` is compiler-enforced privacy — the boundary guard other ecosystems need lint for.
- **Package by feature; the package name is the API prefix**: `payments.Process`, not a `services` package with `ProcessPayment`. No `util`, `common`, `base`, `helpers`, `models` packages — the compiler prints package names in every call site.
- `pkg/` is not required and usually noise — reserve it for code you genuinely support external modules importing. `golang-standards/project-layout` is a community template, **not official Go guidance**; the official reference is go.dev's module-organization docs — verify there.
- Import paths are API: moving an `internal/` package is a local refactor; moving a package other modules import is a **breaking release**.
- The import cycle ban means dependency direction isn't advice in Go — design the package graph before moving, or the compiler will design it for you mid-migration.

## Start flat

```
invoice-tool/
  go.mod
  main.go
  render.go
  render_test.go
```

One package, files split by topic. This is idiomatic for CLIs and small services — resist
scaffolding `cmd/`+`internal/`+`pkg/` around five files; empty taxonomy is the Go smell
equivalent of a junk drawer. Split when a real seam appears (a second binary, a package a
test wants to import in isolation, a subsystem with its own vocabulary).

## Grown service

```
billing/
  go.mod
  cmd/
    server/main.go      # thin: flags/env, wire deps, call run()
    worker/main.go
  internal/
    payments/           # feature package: payments.Process, payments.Refund
    invoicing/
    postgres/           # adapter package named by what it is
    httpserver/         # transport wiring
  go.mod-adjacent files (Makefile, Dockerfile, ...)
```

- `cmd/<name>/` exists to hold multiple binaries; each `main.go` stays thin —
  `main` can't be imported, so logic in it is untestable by construction.
- `internal/` is enforced by the compiler: nothing outside the subtree rooted at
  `internal/`'s parent can import it. Default **everything** into `internal/`; promotion
  out is a deliberate API decision, not a default.
- Single-binary services can skip `cmd/` (`main.go` at root) — add it when the second
  binary arrives, as a move stage.

## Package by feature; the name is the API

A Go package is named at every call site — that makes layer packages read absurdly and
feature packages read like documentation:

```go
// ❌ layer packages: stutter and say nothing
services.ProcessPayment(models.Payment{...})
utils.FormatMoney(...)

// ✅ feature packages: the package name carries the domain
payments.Process(payments.Charge{...})
money.Format(...)
```

Rules:

- Package name = short, lowercase, no underscore, the domain word (`payments`, `pdf`,
  `retry`). The directory name matches it.
- **No `util`, `common`, `helpers`, `base`, `shared`, `models`, `types` packages.** Each is
  a name-by-exclusion ([`00`](./00-structure-principles.md)) — and in Go the bad name is
  repeated at every call site forever. Split by content: `money`, `clock`, `slices2`, or
  inline two-line helpers where they're used.
- Don't stutter: `payments.Process`, not `payments.ProcessPayment` — the prefix is free.
- A central `models` package is also a cycle magnet: every feature imports it, it slowly
  imports features back, and the build dies. Types live in the feature that owns them;
  shared *pure* types get a small content-named package.

## `pkg/` and the "standard layout" myth

- `pkg/` has **no compiler semantics** — it's a naming convention some large repos use for
  "importable by outsiders". If nothing outside the module should import your code, use
  `internal/` and let the compiler enforce it; `pkg/` around internal-only code is a longer
  import path buying nothing.
- `golang-standards/project-layout` is a popular community template, **not official** —
  the Go team's actual guidance (go.dev, "Organizing a Go module") is far more minimal.
  When a user cites the template as gospel, note the distinction and verify against the
  official docs rather than recalling either from memory.

## Import paths are API

- Inside one module, moving a package = updating import lines; the compiler lists every
  site (`go build ./...` is the todo list). Mechanical, safe, stage-able.
- A package under `internal/` is provably private — move freely.
- A package that **other modules** import is public API: its import path appears in *their*
  go.mod/source. Moving or renaming it (including renaming the module path itself) is a
  breaking change — a release/versioning decision (and for v2+ modules, module-path
  versioning rules apply — verify against current docs), not a restructure stage. Go has no
  function-level re-export shim; type aliases forward types only. Prefer: keep the old
  package as a thin forwarding layer you write by hand, or accept the major-version bump.
- This is why the default posture is everything-in-`internal/`: it keeps your future moves
  cheap by construction.

## Migration notes

- Verify loop: `go build ./...` + `go vet ./...` + `go test ./...`; then the census grep
  ([`02`](./02-safe-moves-mechanics.md)) — Dockerfiles building `./cmd/server`, CI paths,
  Makefiles, `//go:generate` directives and `-ldflags -X` symbol paths (both carry
  package paths as strings the compiler won't check).
- Fix import paths mechanically: gopls rename, or search-replace on the exact old import
  string, then let `go build ./...` confirm; `goimports` tidies groups but does not rewrite
  moved paths.
- Breaking an import cycle discovered mid-move is a **design task, not a move**: stop the
  stage, extract the shared dependency into a lower package (or invert with an interface
  defined by the consumer), amend the plan ([`01`](./01-restructure-workflow.md)).
- Layer-bin repos (`controllers/`+`services/`+`models/`) migrate feature-by-feature: each
  stage assembles one feature package from its three slices — expect the hidden
  cross-feature dependencies to surface as cycles; that's the structure being made honest.

## Anti-patterns

- Scaffolding `cmd/`+`internal/`+`pkg/` around a five-file tool.
- `util`/`common`/`helpers`/`models` packages; package names with underscores or stutter.
- Logic in `main.go`; `main` importing nothing but doing everything.
- Exported-by-default: code outside `internal/` with no external consumer story.
- `pkg/` cargo-culted from the community template and cited as "the Go standard".
- Treating a cycle as a move-mechanics problem (papering with a third package named `types`).
- Renaming the module path or a public package's path as a casual restructure stage.

## Review checklist

- [ ] Layout matches size: flat for small; `cmd/` + `internal/` when multiple binaries / real seams exist
- [ ] Everything private-by-default under `internal/`; exports are deliberate
- [ ] Packages are feature/content-named; call sites read as `domain.Verb`; no name-by-exclusion packages
- [ ] `main.go` thin; logic lives in importable packages
- [ ] No import cycles papered over with junk packages; dependency direction designed
- [ ] Public import paths treated as API; moves of them handled as releases
- [ ] `go build ./... && go vet ./... && go test ./...` green per stage; go:generate/ldflags/Docker paths census-grepped
